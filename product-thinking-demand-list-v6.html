需求分析 · 产品方案 · 落地节奏

增长承接与课程履约效率项目

将报名页、短信、定级、商品 ID、订单归因和自动植课，统一放到“渠道线索 → 加微承接 → 学习激活 → 正价购买 → 自动履约”的闭环里设计。

项目定义 这不是单点功能优化，而是一次增长承接与课程履约链路的系统化改造：前端提升有效线索转化，中端提升首课激活和销售承接，后端补齐交易履约底座。
核心目标提升全链路转化效率

不只看加微率，也要看首课、完课、购买和植课成功。

短期抓手报名页 + 企微承接 + 状态短信

先用低成本实验验证 60% → 80% 的真实空间。

长期底座商品 ID + CCID + SID

支撑订单归因、自动履约、续报和拓科。

Analysis

先把“一片式输入”翻译成业务问题

这批输入里混合了运营动作、产品功能、系统底座和风控策略。第一步不是逐条排期，而是先判断它们共同服务哪条业务闭环。

统一问题定义 当前要解决的是：小红书等渠道带来的线索，如何更稳定地完成报名、加微、学习激活、正价购买和自动履约；同时降低人工配置、订单归因和账号倒卖带来的损耗。
1. 不能把加微率当成唯一目标

加微率是中间指标。若加微提升但首课、完课、购买不提升，说明只是把用户提前拉进企微，没有提升业务结果。

2. 不能把 ID 化当成配置需求

体验课 ID、正价课 ID、优惠券 ID、CCID，本质是在补交易履约对象模型，影响支付、植课、归因、续报和拓科。

3. 风控不能一刀切

多设备、多 IP 可能是家庭正常场景，也可能是倒卖风险。应先监控和分层，再做验证、限制和处置。

Scenario First

按场景推导需求

把“要做什么功能”前置还原为“谁遇到了什么阻塞”，再推导对应产品能力。

家

家长：报名后不知道下一步

从内容平台进入后，用户注意力短。如果提交手机号后只是“领取成功”，缺少继续添加老师的明确动机。

推导需求：报名后进入明确第二步，突出“添加老师后领取课表 / 入群 / 获得上课提醒”。
CC

CC：承接与归因不稳定

如果二维码分配、CCID、订单归因不稳定，销售承接和复盘都依赖人工判断。

推导需求：按渠道/批次/CC 动态分配企微；购课链接带 CCID；订单归因可回溯。
SID

Student：级别和首课体验不确定

定级的目标不是“多一个流程”，而是降低首课前阻力，同时让学生进入合适难度。

推导需求：自动定级做兜底，自主定级提升准确性，CC 可查看并修正定级结果。
运

运营：活动商品难配置

体验课、正价课、优惠券如果不能标准化，每次活动都需要人工协作和线下对齐。

推导需求：体验课/正价课/优惠券 ID 化，支持标签、有效期、适用范围、限报和互斥。
风

平台：需要治理倒卖风险

同账号多地、多设备可能是倒卖，也可能是家庭正常使用，策略必须避免误伤。

推导需求：先做异常识别与监控，再引入风险验证、并发上限、白名单和申诉机制。
To Do

这个项目到底要做什么

把链路、指标、功能和系统底座统一成一个可执行目标。

前端：提升有效承接

优化报名页、企微承接页和短信触达，让线索从“报名”更稳定地进入“可沟通、可上课”的状态。

中端：提升学习激活

用自动定级兜底、自主定级补准确性，减少首课前阻力，并通过首课/完课指标验证。

后端：补齐履约底座

通过体验课 ID、正价课 ID、优惠券 ID、CCID、SID 关系，支撑支付、自动植课、归因和复盘。

Priority

再评估优先级：按价值、紧迫度、依赖和风险排序

短期转化实验、长期交易底座、风控治理不应混在同一个需求池中。

1

业务价值

是否直接提升有效线索、首课、完课、正价购买或履约成功。

2

紧迫度

是否影响当前渠道投放、营期承接、销售跟进和短期收入。

3

依赖关系

是否依赖商品、订单、SID、CCID、企微回传等底层能力。

4

实施风险

是否可能误伤用户、引发归因争议、增加运营或研发复杂度。

Sequencing

建议推进顺序

先用可验证的小实验证明转化空间，再投入更重的系统底座。

P0

短期转化闭环

报名页、企微承接、短信状态触发、埋点漏斗、首课阻塞问题。

  • 影响最前端漏斗
  • 上线快，验证快
  • 能直接判断 60% → 80% 是否成立
P1

首课激活与定级

自动定级保留兜底，自主定级补准确性，CC 可见定级结果。

  • 服务首课开始率和完课率
  • 不建议直接下线自动定级
P1

交易履约底座

体验课 ID、正价课 ID、优惠券 ID、CCID、自动植课和 SID 关系。

  • 依赖重，但长期价值高
  • 支撑支付、归因、履约、续报、拓科
谨慎

账号风控治理

先监控异常，再验证、限制和处置，避免误伤正常家庭用户。

优先级矩阵

高价值 / 低依赖

报名页、企微承接、短信触发、埋点：优先做实验。

高价值 / 高依赖

商品 ID、订单归因、自动植课：先建模，再排期。

中价值 / 可验证

定级入口和 CC 可见：用首课、完课和调级率验证。

风险高 / 口径不清

外教语速、低级别 AI 外教跳出等表意不明事项，先补问题定义。

Feature Design

针对每一项能力做具体设计

每个模块都按“目标 → 方案 → 验收 → 边界”展开，避免只停留在功能名。

目标

降低报名阻力，同时让家长在报名后明确知道下一步要添加老师，并可被 CC 稳定承接。

  • 报名页只保留手机号、学生年龄
  • 确认验证码是否必须，平衡转化与虚假手机号
  • 提交后不直接结束流程，而进入添加老师第二步

具体方案

✓二维码页展示具体利益点：课表、入群、上课提醒、答疑服务，而不是只写“添加 CC”。
✓二维码按渠道、批次、CC 动态分配，避免单个企微容量和风控问题。
✓提供长按识别二维码、复制微信号、短信兜底三种路径。
✓企微侧回传添加成功和首次沟通状态，不能用二维码曝光替代加微成功。

目标

短信不是“每天提醒”，而是在用户卡住的节点推动下一步动作。

  • 减少无效打扰
  • 提高各节点召回率
  • 让短信效果可归因

状态触发规则

用户状态短信目标
已报名，未加微提醒添加专属老师
已加微，未下载 App提醒下载并登录
已登录，未开课提醒首课开始
已开课，未完成提醒继续完成体验课
已完成体验课引导测评、反馈或转化

目标

定级不是为了多做一道流程，而是服务两个指标：首课开始率和体验课完课率。

  • 自动定级降低首课前阻力
  • 自主定级提升初筛准确性
  • CC 可见定级结果，便于解释和修正

建议设计

✓自动定级保留为兜底，不建议直接下线。
✓增加自主定级入口，让愿意配合的用户获得更准确结果。
✓CC 端展示自动定级 / 自主定级来源、结果和时间。
✓用首课开始率、完课率、调级率、家长反馈验证方案。

目标

把体验课、正价课、优惠券从一次性运营配置，升级为可追踪、可支付、可自动履约的商品对象。

  • 体验课 ID：绑定产品线、课包、级别、时间、课表、限报
  • 正价课 ID：绑定课包、价格、L1/L2、新签/续报
  • 优惠券 ID：绑定有效期、适用范围和互斥规则

关键规则

✓正价课购课链接支持 CCID，用于订单归属判断。
✓支付成功后自动给对应 SID 植入课程，无需人工处理。
✓同一用户在 60 天内同产品线仅允许一个体验课 ID；再次购买应激活并同步，而不是重复购买。
✓支持不同 SID 对应不同正价课 ID、LP 和 CC。

目标

治理账号倒卖和异常共享，但不能误伤正常家庭用户的多设备、多地点场景。

  • 同账号多 IP / 多地登录
  • 同账号多设备同时在线
  • 同设备多账号或异常切换

分阶段策略

✓第一阶段：只做监控和风险标签，不直接拦截。
✓第二阶段：高风险场景触发短信/验证码/重新登录验证。
✓第三阶段：上线并发上限、踢下线、封禁和人工复核。
✓预留白名单和申诉机制，处理正常家庭跨设备使用。

Requirement List

沉淀后的最终需求清单

这是基于场景、优先级和方案设计整理后的需求池。表意不清的内容暂不直接进入排期。

优先级模块需求项目标 / 验收口径说明
P0报名页优化手机号 + 学生年龄；确认验证码策略；提交后进入添加老师第二步。提升有效留资率与企微添加成功率。先 A/B 测试页面与话术。
P0企微承接页动态 CC 二维码、复制微信号、利益点展示、短信兜底。以企微回传添加成功为核心口径。二维码曝光不能等同加微成功。
P0埋点漏斗覆盖报名、二维码曝光、复制、加微成功、首次沟通、下载、登录、首课、完课、购买。可按渠道、批次、CC、产品线拆分。用于验证 60% → 80% 是否真实有效。
P0短信状态触发按未加微、未下载、未登录、未开课、未完课、已完课触发。提升节点召回率，降低无效打扰。不建议简单 Day1/Day2/Day3 重复发。
P1定级机制保留自动定级兜底；新增自主定级；CC 可见结果和记录。提升首课开始率、完课率，降低调级率。不建议在未验证前直接下线自动定级。
P1体验课 ID 化绑定产品线、课包、级别、开课时间、价格、课表、限报规则。支持体验课标准化售卖、追踪和限报。例如 60 天内同产品线限制。
P1正价课 ID 化绑定课包、级别、价格、课表；支持双课包 L1 新签 + L2 续报。支持 H5 支付和支付后自动植课。交易履约核心底座。
P1优惠券 ID 化支持有效期、适用产品线、指定正价课 ID、限用和互斥。支持活动配置、优惠策略和复盘。需明确和商品包、订单的关系。
P1CCID 归因与自动植课购课链接支持 ccid；订单记录归属；支付成功给对应 SID 植课。提升归因准确率，降低人工植课成本。处理重复购买、换 CC、多个 SID 边界。
P2User-SID-课包关系明确 UID、手机号、微信号、SID、体验课、正价课、LP、CC 关系。支撑续报、拓科、服务归属和订单复盘。长期数据资产。
谨慎账号风控治理多 IP、多设备、账号共享监控；风险验证；并发上限；异常处置。降低倒卖账号和异常共享。先监控再限制，保留白名单和申诉机制。
暂不直接进入需求池：“下周二下班前外教语速提速”“P1 部分下周二下班前解决（除低级别 AI 外教主动跳出）”当前表意不完整，建议先补充问题描述、影响范围、验收标准、责任系统和业务优先级。
Roadmap

建议落地节奏

分阶段推进，避免一开始就进入大系统改造。

1

第 1 阶段｜口径与快速实验

  • 确认加微率分母与企微回传能力
  • 补齐从报名到购课的漏斗埋点
  • 报名页与二维码页 A/B 测试
  • 短信状态触发简版上线
2

第 2 阶段｜首课激活与对象建模

  • 自动定级与自主定级并行验证
  • 定义 Trial SKU / Paid SKU / Coupon
  • 明确 UID、SID、订单、CC、LP 关系
  • 梳理限报、重复购买、优惠券互斥规则
3

第 3 阶段｜自动履约与风控

  • H5 支付后自动植课
  • 建立履约成功率和人工干预监控
  • 设备/IP 风控从监控升级到限制
  • 建立白名单、申诉和人工复核机制
