增长链路与课程履约需求分析

这份需求不是已经拆好的功能清单，而是一片原始业务输入。我的处理方式是：先还原业务目标，再梳理完整链路，最后拆成可验证、可排期、可落地的产品模块。

增长承接首课激活交易履约账号风控组织归因
1. 不直接逐条排期

先判断每条输入背后的业务问题，避免把症状当需求。

2. 不只优化加微率

加微率只是中间指标，最终要看首课、完课、购买和履约。

3. 不把 ID 当字段

体验课、正价课、优惠券、CCID，本质是交易履约对象模型。

4. 风控先监控再限制

防倒卖要做，但需要控制误伤，不能影响正常家庭多设备使用。

01｜30 秒结论

如果只向上汇报一页，我会先讲这三点：业务目标、关键风险、推进方式。
核心判断：这批需求应被定义为“从渠道获客到课程履约的转化效率项目”，不是单纯的落地页优化、短信提醒或商品 ID 改造。

短期抓转化漏损

优先验证落地页留资、加微、下载登录、首课开始这些关键环节，而不是只追一个加微率数字。

中期补交易底座

体验课 ID、正价课 ID、优惠券 ID、CCID、自动植课要作为一个对象模型设计，不能零散加字段。

风控谨慎上线

多 IP/多设备治理需要先监控、分层验证、再限制；同时必须有白名单和申诉机制。

02｜把原始输入翻译成业务目标

业务方提的是动作和方案，产品需要先翻译成目标和指标。
增长落地页、加微、短信、外呼：解决线索承接效率
激活定级、课程解锁、外教语速：解决首课开始和体验质量
履约课程 ID、优惠券、支付、植课：解决商品售卖和交付自动化
治理多设备、多 IP、共享账号：解决倒卖和账号滥用风险

03｜完整业务链路

这条链路串起来之后，才能判断每个需求到底卡在哪一环。

获客

小红书 / 渠道曝光 → 报名页访问

留资

手机号 + 孩子年龄 → 领课成功

承接

专属 CC 企微 → 短信 / 外呼召回

激活

下载 App → 登录 → 定级 → 首课

转化

体验课完课 → CC 跟进 → 正价购买

履约

自动植课 → 服务承接 → 续报 / 拓科

关键判断：加微率只是承接环节指标，不能替代后续首课率、完课率、正价转化率和履约成功率。

06｜对象模型：第 5/9 条是底座，不是字段

体验课、正价课、优惠券、用户、孩子、CC、LP 的关系如果不先建模，后续支付、植课、归因、续报都会混乱。

User 家长

uid手机号微信号家长身份唯一，但学习主体是孩子。

Child 孩子

child_id年龄level一个家长可以有多个孩子，不同孩子可对应不同课包。

Trial SKU 体验课

trial_id产品线级别课表支持限报规则，例如 60 天内同产品线仅一个体验课。

Paid SKU 正价课

paid_id课包价格L1/L2支持 H5 支付、双课包、新签/续报、支付后自动植课。

Coupon 优惠券

coupon_id有效期适用范围可定向产品线或某些正价课 ID，需要限用、互斥和有效期。

Attribution 归因

cc_idlp_idorder_id购买链接带 CCID，订单、课程和服务归属要可追踪。

08｜建议落地节奏

用分阶段方式降低风险：先验证漏斗，再补底座，最后做自动化和风控强化。
1

第 1 阶段：统一口径 + 快速实验

  • 确认加微率、首课率、完课率口径
  • 落地页和企微承接 A/B 测试
  • 短信从“按天”改为“按状态”触发的简版
2

第 2 阶段：首课激活 + 商品建模

  • 自动定级和自主定级并行验证
  • 定义 Trial SKU / Paid SKU / Coupon
  • 明确 CCID、孩子、订单和课包关系
3

第 3 阶段：自动履约 + 风控治理

  • H5 支付后自动植课
  • 搭建履约成功率和人工干预监控
  • 设备/IP 风控从监控逐步升级到限制

09｜我会优先追问的问题

这些问题能帮助判断是真需求、伪需求，还是已有方案不完整。
指标口径
60% / 80% 加微率的分母是什么？
访问、留资、领课成功、有效线索，不同分母会导致不同结论。
后链路价值
加微后的下载率、首课率、完课率、正价转化率是多少？
防止只优化中间动作，没有带来最终业务增长。
短信策略
短信按 Day1/Day2 群发，还是按用户状态触发？
状态触发更精准，也更容易评估召回效果。
定级目的
自动定级要解决准确性，还是降低首课前阻力？
决定是下线、保留兜底，还是做自主定级入口。
商品模型
体验课、正价课、优惠券、课包、课表、级别如何关联？
这是支付、植课、续报和拓科的系统底座。
风控边界
什么行为确定是倒卖？什么是家庭正常多设备？
风控不能只看拦截率，还要看误伤率和申诉成本。

如果我来对接，第一步不会直接写 PRD

我会先拉齐三件事：① 现有漏斗数据和指标口径；② 课程商品/用户/孩子/CC/LP 的对象关系；③ P0 转化实验和 P1 底座建设的边界。这样能避免把一片式原始需求直接拆成零散功能，最后做了很多点，但业务结果没有闭环。
