06｜对象模型：第 5/9 条不是“加几个 ID”

体验课、正价课、优惠券、用户、孩子、CC、LP 的关系如果不先建模，后续支付、植课、归因、续报都会混乱。

User 家长

uid手机号微信号家长身份唯一；但家长不是学习主体，孩子才是课程匹配主体。

Child 孩子

child_id年龄level同一家长可有多个孩子，不同孩子可购买不同课程包。

Trial SKU 体验课

trial_id产品线级别课表支持限报：例如同用户 60 天内同产品线只允许一个体验课 ID。

Paid SKU 正价课

paid_id课包价格L1/L2支持 H5 支付、双课包、新签/续报、支付后自动植课。

Coupon 优惠券

coupon_id有效期适用范围可定向产品线或某些正价课 ID，需要互斥、限用和有效期规则。

Attribution 归因

cc_idlp_idorder_id购买链接带 CCID，订单、课包、服务归属要能追踪和复盘。

08｜关键产品判断：我不会直接给结论，而是先问这 8 个问题

面对原始需求，问对问题本身就是产品能力。
问题方向我会追问为什么重要
指标口径加微率 60% / 80% 的分母是什么？访问、留资、有效线索，还是领课成功？不同口径对应完全不同的优化策略。
后链路价值加微后的下载率、首课率、完课率、正价转化率是多少？避免只提升加微，不提升业务结果。
渠道差异小红书用户和其他渠道用户的年龄、意图、价格敏感度是否不同？决定落地页、短信话术和 CC 承接策略。
短信策略短信是按天触发，还是按用户状态触发？是否可区分未加微/未登录/未首课？状态触发更精准，也更容易归因。
定级目的自动定级要解决准确性，还是降低首课前阻力？决定是下线、保留兜底，还是加强自主定级。
商品模型体验课 ID、正价课 ID、优惠券 ID、课包、课表、级别如何关联？决定后续支付、植课、续报能否自动化。
归因规则一个家长多个孩子、多课包、多 CC/LP 时，订单归属和服务归属怎么算？决定销售激励、复盘和续报归因是否清晰。
风控边界哪些行为确定是倒卖？哪些是家庭正常多设备？误伤后如何申诉？风控不能只看拦截率，还要看误伤率。

09｜落地路径：先轻量验证，再补底座

既不能只做短期小修，也不能一上来陷入大系统建设。建议分三阶段。
第 0 步：统一口径
确认加微率、留资率、首课率、完课率、正价转化率、自动植课成功率的定义和分母。没有口径统一，后面所有优化都可能失真。
第 1 步：短期转化实验
优化落地页领课链路、领课成功页企微承接、未加微/未登录/未首课的状态短信；同时按渠道、年龄、课程包拆分看后链路指标。
第 2 步：首课激活优化
自动定级不建议直接下线，先作为兜底；新增自主定级入口获取更准结果；CC 端可见自动定级结果、来源和可修正入口。
第 3 步：交易履约底座
设计体验课、正价课、优惠券、订单、课包、CCID、LP/CC 归属对象模型，再推进 H5 支付、自动植课和拓科入口。
第 4 步：风控灰度
先做监控和风险评分，再做风险验证，最后才做设备数限制/踢下线；必须配套白名单、申诉和人工兜底。

10｜可直接发给 +2 的文字版

这段可以直接复制发，语气保持认真、有思考、不过度表现。

我对这批原始需求的思考

我又重新看了一遍这份需求 list。这次我没有把它当成一组已经整理好的功能需求，而是把它当成一片比较原始的业务输入来看。

我的感受是，这里面混在一起的东西比较多：有业务目标，比如提升加微率和体验课转化；有运营动作，比如短信、外呼、CC 跟进；有产品功能，比如落地页、企微二维码、H5 支付；有系统底座，比如体验课 ID、正价课 ID、优惠券 ID、用户 UID；也有风控策略，比如多 IP、多设备、账号倒卖。

所以如果是我来对接，我不会第一步就逐条拆功能和排期，而是会先做一层产品翻译：把业务方的一片式表达，翻译成清晰的业务链路、指标问题、对象模型和优先级判断。

1. 我对整体目标的理解

我理解这批需求背后的总目标，不是“做几个功能”，而是提升小红书等渠道用户从报名、加微、下载 App、上体验课，到购买正价课和自动履约的整体转化效率，同时降低人工承接、课程配置和账号倒卖带来的损耗。

这里我会特别注意：加微率不是最终目标，它只是中间指标。如果加微率提升了，但下载率、首课率、完课率、正价转化率没有提升，那说明只是把用户提前拉进企微，并没有真正提升业务结果。

2. 我会先画完整业务链路

我会先把链路还原出来：小红书/渠道曝光 → 报名落地页访问 → 填手机号和孩子年龄 → 领课成功 → 添加 CC 企微 → 下载 App/登录 → 定级/自动定级 → 体验课解锁 → 首课开始 → 体验课完课 → CC 跟进转化 → 购买正价课 → 系统自动植课 → 持续上课/续报/拓科。

对应每一环都要补指标，比如留资率、加微率、首次有效沟通率、下载率、登录率、定级率、首课开始率、完课率、正价转化率、自动植课成功率和续报/拓科率。这样才能判断每个需求到底卡在哪个环节，而不是谁声音大谁优先。

3. 我会把需求拆成几个模块

  • 增长承接：落地页、加微、短信、外呼，解决线索来了以后有没有被有效承接。
  • 首课激活：自动定级、自主定级、课程解锁、外教语速，解决用户能不能低阻力开始上课。
  • 交易履约：体验课 ID、正价课 ID、优惠券 ID、H5 支付、自动植课，解决课程商品能不能标准化售卖和自动交付。
  • 组织归因：CCID、LP、CC、用户、孩子、课包之间的归属关系，解决订单和服务归因问题。
  • 账号风控：多 IP、多设备、多地登录和倒卖治理，解决业务风险，但要避免误伤正常家庭用户。

4. 优先级上我会这样判断

P0 是短期直接影响转化的链路：报名落地页领课链路、领课成功后跳转专属 CC 企微、未加微/未登录/未首课的状态短信、外教语速和 P1 体验问题。

P1 是首课激活和交易履约底座：自动定级不建议直接下线，可以作为兜底；自主定级作为更准确输入。同时开始设计体验课、正价课、优惠券、订单、CCID、LP/CC 的对象关系。

风控类需求要谨慎推进：我会先做监控和风险评分，再做风险验证，最后才做强限制或踢下线。因为家庭用户本身可能存在多设备、多地区使用，如果一上来强拦截，可能会伤害真实付费用户。

5. 我会重点追问几个问题

  • 加微率 60%/80% 的分母是什么？是访问、留资、领课成功，还是有效线索？
  • 小红书用户的首课率、完课率、正价转化率是否也比其他渠道更好？
  • 短信应该按天触发，还是按用户状态触发？是否能区分未加微、未登录、未首课？
  • 自动定级到底是为了解决准确性，还是为了降低首课前阻力？
  • 一个家长多个孩子、多课包、多 LP/CC 时，订单和服务归属如何判断？
  • 风控上哪些行为确定是倒卖，哪些可能只是正常家庭多设备使用？

我的整体判断是：这批需求不能直接当功能池处理。它更像是一个从增长承接到课程履约的业务系统改造。短期可以先通过落地页、企微承接和状态短信提升转化；中期必须补体验课/正价课/优惠券/订单/归因的底座；风控要基于数据逐步上线，避免一开始就强限制导致误伤。
