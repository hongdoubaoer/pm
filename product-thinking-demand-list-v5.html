增长承接与课程履约需求分析

这批输入混合了渠道转化、短信触达、定级、商品配置、订单归因、自动履约和账号风控。建议先按业务链路和场景重新建模，再沉淀为可排期、可验收的需求清单。

增长承接 首课激活 交易履约 组织归因 账号风控
核心目标

提升渠道线索从报名到首课、完课、购课、植课的整体转化效率。

关键判断

加微率是中间指标，需要和首课率、完课率、正价转化一起看。

体验课、正价课、优惠券、CCID 需要统一进入商品与交易模型。

推进原则

Executive Summary

01｜核心结论

本页先给判断，再说明待确认问题、优先级、场景、链路、指标和最终需求清单。
这应被定义为“增长承接与课程履约效率项目”不是单独优化报名页、短信、定级或商品 ID，而是把渠道线索从报名、加微、学习激活、购买到自动履约串成闭环。
短期先做转化实验报名页、二维码页、短信触达、埋点和首课阻塞问题。
中期补交易底座体验课 ID、正价课 ID、优惠券 ID、CCID 归因、自动植课。
风控谨慎推进先监控异常，再风险验证和限制，避免误伤正常家庭用户。
Clarifications

02｜进入方案前需要先确认的问题

这些问题建议放在前面，因为它们会直接影响方案边界、验收指标和研发排期。
指标口径
60% / 80% 加微率的分母是什么？

是报名页访问、完成留资、领课成功，还是有效线索？不同分母对应完全不同的优化空间。

真实加微确认
加微成功能否由企微侧回传？

二维码曝光、点击复制微信号不能等同于加微成功。最好由企微回传好友添加状态和首次沟通状态。

后链路表现
加微后的下载、登录、首课、完课、正价转化分别是多少？

如果加微率提升但后链路不提升，说明只优化了中间动作，没有提升业务结果。

验证码策略
报名页手机号是否必须验证码？

字段越少转化越高，但如果没有验证码，可能引入虚假手机号，影响 CC 承接和数据质量。

定级目标
自动定级是为了准确性，还是为了降低首课前阻力？

如果目标不同，方案会不同：保留兜底、自主定级、CC 修正、还是下线自动定级。

商品模型
体验课、正价课、优惠券、课表、级别如何关联？

这决定支付、植课、限报、重复购买、续报、拓科和订单归因能否长期跑通。

Scenario Thinking

04｜按场景推导需求

每个功能都要回到“谁在什么场景下遇到什么阻塞”，否则容易把运营动作误写成产品需求。
家

家长：领课后不知道下一步做什么

家长从小红书进入后注意力很短。如果提交手机号后只展示“领取成功”，下一步动机不足。

产品推导：提交后进入明确第二步：“课程已锁定，添加老师后领取课表 / 入群 / 获得上课提醒”。
CC

CC：线索归属和订单归因不清

如果链接不带 CCID，体验课 / 正价课没有 ID，后续跟进、绩效、复盘和植课都会依赖人工。

产品推导：购课链接带 CCID，订单记录归属；SID 维度绑定课包、LP、CC 和服务状态。
学

Student / SID：级别和首课承接不稳定

自动定级不是目的，目的是降低首课前阻力，同时保证课程难度大致匹配。

产品推导：自动定级做兜底，自主定级做准确性，CC 可查看定级结果并在必要时修正。
运

运营：活动商品难配置、难复盘

如果体验课、正价课、优惠券不能标准化配置，每次活动都会变成人工协作。

产品推导：体验课 / 正价课 / 优惠券统一 ID 化、标签化、可定向、可追踪。
风

平台：要防倒卖，但不能误伤正常家庭

家庭用户可能天然存在多设备、多地区使用，不能简单按 IP 或设备一刀切。

产品推导：先做异常监控和风险验证，再根据证据上线并发限制、踢下线和封禁策略。
End-to-end Journey

05｜完整业务链路

链路明确后，需求才能映射到具体阻塞点，避免变成“谁提得急谁优先”。
渠道获客小红书 / 投放 / 转介绍进入报名页。
报名留资手机号、学生年龄；确认验证码策略。
销售承接动态分配 CC 企微，短信兜底，企微回传加微结果。
学习激活下载 App、登录、定级 / 自动定级、解锁首课。
体验转化首课开始、体验课完课、CC 跟进正价转化。
交易履约H5 支付、CCID 归因、自动植课。
续报拓科持续上课、续报、拓科入口和服务承接。

判断标准：每个需求都要能回答“它解决链路哪一环？影响哪个指标？有没有更低成本替代方案？”

Solution Detail

07｜关键产品方案

这里把最影响转化的方案说具体，便于后续拆 PRD 和验收。

报名页与企微承接

1
报名页只保留必要字段

手机号、学生年龄；同步确认是否必须短信验证码，避免虚假手机号影响 CC 承接。

2
提交后进入明确第二步

不要只显示“领取成功”，而是提示“课程已锁定，添加老师后领取课表 / 入群 / 获得上课提醒”。

3
二维码页展示利益点

不只是“添加 CC”，而是说明添加后的具体价值：课表、上课提醒、问题答疑、入群服务。

4
二维码动态分配

按渠道、批次、CC 动态分配，避免单个企微容量、风控和归属混乱。

5
提供多重兜底

长按识别二维码、复制微信号、短信兜底；埋点覆盖二维码曝光、复制、企微添加成功和首次沟通。

短信触达策略

用户状态触达目标示例动作
已报名，未加微添加老师提醒添加专属老师领取课表 / 入群。
已加微，未下载 App下载 App发送下载入口和登录指引。
已登录，未开课开始首课提醒课程已解锁，提示上课时间。
已开课，未完成继续学习提醒继续完成体验课。
已完成体验课测评 / 转化引导查看反馈、测评结果或联系老师。

不建议简单 Day1 / Day2 / Day3 重复发送同类短信；状态触发更精准，也更容易评估召回效果。

Object Model

08｜对象模型

第 5 / 9 条不是“加几个 ID”，而是交易履约和数据归因的基础。对象关系不清，后续支付、植课、续报、拓科都会混乱。

User 家长

uid手机号微信号家长是账户、沟通和支付主体。

Student 学生

sid年龄level学生是上课主体；同一 User 下可有多个 SID。

Trial SKU 体验课

trial_id产品线级别课表支持限报，例如 60 天内同产品线只允许一个体验课 ID。

Paid SKU 正价课

paid_id课包价格L1/L2支持 H5 支付、双课包、新签/续报、支付后自动植课。

Coupon 优惠券

coupon_id有效期适用范围可定向产品线或指定正价课 ID，需要限用与互斥规则。

Attribution 归因

cc_idlp_idorder_id购买链接带 CCID，订单、SID、课程和服务角色要可追踪。
Final Requirement List

09｜沉淀后的最终需求 List

这是基于场景、链路、指标和优先级整理后的需求清单。表意不清的事项暂不直接进入需求池。
优先级需求模块需求项目标 / 验收口径备注
P0报名页优化手机号 + 学生年龄领课；确认验证码策略；提交后进入“添加老师”第二步。提升有效留资率与企微添加成功率。先 A/B 测试页面与话术。
P0企微承接页展示动态 CC 二维码、复制微信号、添加利益点和短信兜底。以企微回传的添加成功为核心验收口径。避免用二维码曝光替代加微成功。
P0埋点与漏斗覆盖报名、二维码曝光、复制微信号、企微添加成功、首次沟通、下载、登录、首课、完课、购买。能按渠道、批次、CC、产品线拆漏斗。没有埋点就无法判断 60% → 80% 是否真实有效。
P0短信状态触发按用户状态触发短信：未加微、未下载、未登录、未开课、未完课、已完课。提升各节点召回率，降低无效打扰。不建议简单每日重复发送。
P1定级机制保留自动定级兜底；新增自主定级入口；CC 可见自动定级结果和记录。降低首课前阻力，提升定级准确性。用首课开始率、完课率、调级率验证。
P1体验课 ID 化体验课 ID 绑定产品线、课包、级别、开课时间、价格、课表；支持限报规则。支持体验课标准化售卖、追踪和限报。如 60 天内同产品线只允许一个体验课 ID。
P1正价课 ID 化正价课 ID 绑定课包、级别、价格、课表；支持双课包 L1 新签 + L2 续报。支持 H5 支付和支付后自动植课。交易履约核心底座。
P1优惠券 ID 化支持有效期、适用产品线、指定正价课 ID、限用和互斥。支持活动配置、优惠策略和效果复盘。需明确与商品包、订单的关系。
P1CCID 归因与自动植课购课链接支持 ccid；订单记录归属；支付成功后自动给对应 SID 植入课程。提升归因准确率，降低人工植课成本。需处理重复购买、换 CC、多个 SID 等边界。
P2User-SID-课包关系明确 UID、手机号、微信号、SID、体验课 ID、正价课 ID、LP、CC 的对应关系。支撑续报、拓科、服务归属和订单复盘。长期数据资产。
谨慎账号风控治理多 IP、多设备、账号共享监控；风险验证；并发上限；异常处置。降低倒卖账号和异常共享。先监控再限制，保留白名单和申诉机制。
暂不直接进入需求池：“下周二下班前外教语速提速”“P1 部分下周二下班前解决（除低级别 AI 外教主动跳出）”当前表意不完整，建议先补清楚问题描述、影响范围、验收标准和责任系统，再决定是否纳入 P0 修复项。
Roadmap

10｜建议落地节奏

先补数据与短期实验，再做商品和履约底座，最后推进风控治理。
1

第 1 阶段｜口径与快速实验

  • 确认加微率分母与企微回传能力
  • 补齐从报名到购课的漏斗埋点
  • 报名页与二维码页 A/B 测试
  • 短信状态触发简版上线
2

第 2 阶段｜首课激活与对象建模

  • 自动定级与自主定级并行验证
  • 定义 Trial SKU / Paid SKU / Coupon
  • 明确 UID、SID、订单、CC、LP 关系
  • 梳理限报、重复购买、优惠券互斥规则
3

第 3 阶段｜自动履约与风控

  • H5 支付后自动植课
  • 建立履约成功率和人工干预监控
  • 设备/IP 风控从监控升级到限制
  • 建立白名单、申诉和人工复核机制

最终处理思路

这批需求的重点不是把原始 list 逐条翻译成功能，而是先统一业务目标、指标口径和对象关系。短期用报名页、企微承接、短信触达和埋点验证转化提升；中期用体验课、正价课、优惠券、CCID 和 SID 关系补齐交易履约底座；风控在有数据证据后分阶段上线，避免误伤正常用户。
