增长链路与课程履约需求分析

这不是一份已经整理好的功能需求池，而是一片混合了增长目标、运营动作、系统能力和风控规则的原始业务输入。我的处理方式是：先还原场景，再建立业务链路，最后沉淀成可排期、可验收的需求 list。

Business Framing

02｜从业务视角重新理解这批需求

业务方给出的不是“标准需求”，而是业务现象、运营动作、产品方案、技术设想的混合物。
增长承接
问题小红书等渠道带来的线索，是否能顺利从兴趣进入销售/服务承接？

对应输入落地页、加微、短信、外呼。
首课激活
问题用户留资后，能否尽快下载、登录、定级并开始第一节课？

对应输入自动定级、自主定级、课程解锁、外教语速、P1 问题。
交易履约
问题体验课、正价课和优惠券能否被标准化售卖、支付、归因和自动植课？

对应输入体验课 ID、正价课 ID、优惠券 ID、H5 支付、自动植课。
风险治理
问题如何降低账号共享和闲鱼倒卖，同时不影响正常家庭多设备上课？

对应输入多 IP、多设备、风险验证、并发限制。
Scenario Thinking

03｜先按场景推导，而不是按功能堆叠

每个功能都要回到“谁在什么场景下遇到什么阻塞”。
家

家长：我已经领课了，下一步该干什么？

家长从小红书进入后，注意力很短。如果领课后没有明确下一步，就会流失。

产品推导：落地页必须把“领课成功 → 添加专属顾问 → 下载登录 → 开始首课”做成连续动作。
CC

CC：我怎么知道这个订单/用户归谁？

如果 CCID、体验课 ID、正价课 ID、孩子和订单关系不清，后续跟进、归因、绩效都会出问题。

产品推导：购买链接带 CCID，订单记录归因；孩子维度绑定课包和服务角色。
课

孩子：应该上哪个级别？什么时候开始？

自动定级不是目的，目的是减少首课前阻力，同时尽量保证级别匹配。

产品推导：自动定级做兜底，自主定级做准确性，CC 可见结果并可修正。
运

运营：商品、优惠券和课包怎么配置？

如果每次活动都靠人工配置和人工植课，就无法规模化，也无法复盘不同活动效果。

产品推导：体验课/正价课/优惠券需要 ID 化、标签化、可定向、可追踪。
风

平台：怎么防止倒卖，又不误伤真实家庭？

家庭用户天然可能多设备、多地区使用，风控不能简单按设备/IP 一刀切。

产品推导：先监控，再风险验证，再限制并发；保留白名单和申诉机制。
End-to-end Journey

04｜完整业务链路

只有把链路串起来，才知道每个需求解决的是哪一环，而不是谁声音大谁优先。
渠道获客小红书 / 投放 / 转介绍进入报名页。
报名留资填写手机号、孩子年龄，完成领课。
销售承接展示专属 CC 企微，短信/外呼召回未加微用户。
学习激活下载 App、登录、定级或自动定级，解锁首课。
体验转化完成体验课后由 CC 跟进，引导正价课购买。
交易履约H5 支付、CCID 归因、系统自动植课。
续报拓科服务承接、持续上课、续报和拓科入口。

判断标准：任何单点需求都要能映射到这条链路上的某个阻塞点，并能对应一个可观察指标。

Object Model

06｜先定义对象模型，再写功能

第 5 / 9 条不是“给课、券、链接加 ID”，而是交易履约底座。如果对象关系不清，后续支付、植课、归因、退款、拓科都会混乱。

User 家长

uid手机号微信号家长是账户和支付主体，但学习主体是孩子。

Child 孩子

child_id年龄level一个家长可有多个孩子，不同孩子可对应不同课包。

Trial SKU 体验课

trial_id产品线级别课表支持限报，例如 60 天内同产品线仅一个体验课。

Paid SKU 正价课

paid_id课包价格L1/L2支持 H5 支付、双课包、新签/续报、支付后自动植课。

Coupon 优惠券

coupon_id有效期适用范围可定向产品线或指定正价课 ID，需要限用和互斥规则。

Attribution 归因

cc_idlp_idorder_id购买链接带 CCID，订单、孩子、课程和服务角色要可追踪。

07｜沉淀后的最终需求 List

这是把原始输入整理后的可执行需求列表。它比原始 list 更适合评审、排期和验收。
优先级需求模块需求项目标 / 验收口径备注
P0报名落地页优化手机号 + 孩子年龄领课；领课成功页展示专属 CC 企微二维码、微信号复制、下一步指引。提升留资率、加微率，并观察首课开始率。必须按渠道、年龄、产品线拆数据。
P0短信自动触发从固定 Day1/Day2/Day3 文案，升级为按用户状态触发：未加微、未下载、未登录、未上首课、未完课。提升未完成下一步用户的召回率。先做简版状态触发，避免一开始做复杂营销自动化。
P0首课体验问题外教语速、P1 问题、低级别 AI 外教主动跳出等体验阻塞快速修复。提升首课开始率、完课率，降低投诉。这是后链路承接，不应被“加微率”掩盖。
P1定级机制优化保留自动定级兜底；新增自主定级入口；CC 可见自动定级结果、来源和定级记录。降低首课前阻力，同时提升级别匹配准确性。不要简单下线自动定级，要看首课率和完课质量。
P1体验课 ID 化体验课 ID 绑定产品线、课包、级别、开课时间、价格、课表；支持限报规则。支持体验课标准化售卖、追踪和限报。例如同用户 60 天内同产品线只允许一个体验课 ID。
P1正价课 ID 化正价课 ID 绑定课包、级别、价格、课表；支持双课包 L1 新签 + L2 续报。支持正价课 H5 支付和支付后自动植课。这是交易履约核心底座。
P1优惠券 ID 化优惠券 ID 支持有效期、适用产品线、指定正价课 ID、限用与互斥规则。支持活动配置和价格策略复盘。需要明确优惠券与商品包、订单的关系。
P1CCID 归因与自动植课购课链接支持 ccid 参数；订单记录归属；支付成功后自动给账户植入对应课程。提升归因准确率，降低人工植课成本。需要处理重复购买、换 CC、多个孩子等边界。
P2用户-孩子-课包关系明确 UID、手机号、微信号、孩子、体验课 ID、正价课 ID、LP、CC 的关系。支撑续报、拓科、服务归属和订单复盘。这是长期数据资产，不只是展示字段。
谨慎账号风控治理多 IP、多设备、账号共享监控；风险验证；并发上限；异常处置。降低倒卖账号和异常共享。先监控再限制，避免误伤正常家庭用户。
Prioritization

08｜优先级判断：短期转化与长期底座分开

不能把所有需求放进同一个池子排。短期实验、长期底座、风控治理的节奏不同。
业务影响高
长期价值高
依赖低
可快速验证

P0｜短期转化实验

  • 落地页领课和加微链路
  • 短信状态触发简版
  • 外教语速 / P1 阻塞修复
  • 首课开始率与完课率埋点

P1｜首课激活优化

  • 自动定级做兜底
  • 自主定级提升准确性
  • CC 可见定级结果
  • 后续按完课质量验证
依赖高
需先建模

P1｜交易履约底座

  • 体验课 / 正价课 / 优惠券 ID 化
  • 商品标签体系
  • H5 支付 + CCID 归因
  • 支付后自动植课

谨慎推进｜账号风控

  • 先做多设备 / 多 IP 监控
  • 再做风险验证
  • 最后做并发限制和踢下线
  • 必须有白名单和申诉机制
Roadmap

09｜建议落地节奏

先拿短期业务结果，再补长期系统能力，避免一开始就陷入大而全的底座改造。
1

第 1 阶段｜拉齐口径 + 快速验证

  • 确认加微率分母和数据口径
  • 补齐从留资到购课的漏斗埋点
  • 落地页 + 企微承接 A/B 测试
  • 短信状态触发简版上线
2

第 2 阶段｜激活优化 + 对象建模

  • 自动定级与自主定级并行验证
  • 定义 Trial SKU / Paid SKU / Coupon
  • 明确 UID、孩子、订单、CC、LP 关系
  • 梳理重复购买、限报、优惠券互斥规则
3

第 3 阶段｜自动履约 + 风控治理

  • H5 支付后自动植课
  • 建立履约成功率和人工干预监控
  • 设备/IP 风控从监控升级到限制
  • 建立白名单、申诉和人工复核机制
Questions

10｜我会优先追问的问题

这些问题用来判断是真需求、伪需求，还是业务方案还没有想清楚。
方向关键问题为什么重要
指标口径60% / 80% 加微率的分母是什么？访问、留资、领课成功还是有效线索？分母不同，优化动作和业务判断完全不同。
后链路价值加微后的下载率、首课率、完课率、正价购买率是多少？防止只优化中间动作，没有带来真实业务增长。
短信策略短信是按 Day1/Day2 群发，还是按用户状态触发？状态触发更精准，也更容易评估召回效果。
定级目的自动定级要解决准确性，还是降低首课前阻力？决定是下线、保留兜底，还是做自主定级入口。
商品模型体验课、正价课、优惠券、课包、课表、级别如何关联？这是支付、植课、续报和拓科的系统底座。
风控边界什么行为确定是倒卖？什么是家庭正常多设备使用？风控不能只看拦截率，也要看误伤率和申诉成本。

如果我来对接，第一步不会直接写 PRD

我会先拉齐三件事：第一，现有漏斗数据和指标口径；第二，体验课、正价课、优惠券、用户、孩子、CC、LP 的对象关系；第三，P0 转化实验和 P1 底座建设的边界。这样能避免把一片式原始需求直接拆成零散功能，最后做了很多点，但业务结果没有闭环。
